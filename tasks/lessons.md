# 教訓

## 「取れたデータ」と「求められたデータ」を混同しない

**事象**: 移籍データの可視化を依頼され、`division-ranking/*/transfersExperts|transfersLosers` を主データに据えて実装した。しかしこれは「儲かった/損した移籍の上位数件」というランキングの抜粋であり、ユーザーが求めていた「どの選手がどのフェーズでいくらで落札されたか」という**全取引の記録ではなかった**。完成後に指摘を受けて全面的に作り直した。

**原因**: 最初に 200 が返ったエンドポイントで満足し、それが要件を満たすか検証しなかった。「移籍」という語が付くエンドポイントを見つけた時点で探索を打ち切っている。

**再発防止**:
- API 探索では「動いた」で止めず、**返ってきたデータが要件の粒度・母集団と一致するか**を確認する。件数が不自然に少ない（18件しかない等）のは母集団が違う兆候である。
- ランキング系（`*-ranking`）は集計結果であり、生データは別にあると疑う。履歴・ログ系（`*-history`）を先に探す。

## 一括取得の経路だけを見て「不可能」と結論しない

**事象**: 選手名の解決で、プール API（`championship-players-pool`）が現行シーズン分しか返さないことを確認し、「過去の選手の名前は解決不能」とユーザーに報告した。実際には `/championship-player/{playerId}` で個別に取得でき、全件解決できた。

**原因**: 「名前は一括で引くもの」という思い込みで、個別取得の経路を試していなかった。

**再発防止**: 「できない」と報告する前に、一括取得・個別取得・履歴経由の3方向を試す。不可能の断定は、可能性を潰し切ってから行う。

## 推測で決め打ちせず、実リクエストを捕獲する

**事象**: フロントバンドルの解析だけでエンドポイントとヘッダを組み立てたところ、必須ヘッダ（`application` / `client-version`）が欠けて全リクエストが 400 になった。ユーザーがブラウザから実リクエストを提供してくれて解決した。

**再発防止**: SPA の内部 API を利用する際は、バンドル解析を出発点としつつ、**実際に飛んでいるリクエストのヘッダ一式を最初に確認する**。認証ヘッダだけでは足りないことが多い。
